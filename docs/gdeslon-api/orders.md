# Заказы (API по продажам, JSON)

Источник: https://gdeslon.ru/faq/26/ (перечитано 2026-10-07, текст не менялся) · Контекст: Sales · Порт: `OrderRepository`

`POST https://gdeslon.ru/api/orders/`, `Content-Type: application/json`, HTTP Basic `USER_ID:API_KEY`
(ключи: https://gdeslon.ru/api_settings/orders). Отчёт по продажам аккаунта, server-to-server.
Документация (пример 2014 года) указывает `https://www.gdeslon.ru/api/orders/` и `curl -L` — см. «Два бэкенда».

## Хост, авторизация, HTTP (проверено 2026-10-07)

- `gdeslon.ru` — бэкенд Django REST Framework (тексты ошибок DRF, `Vary: Accept-Language, Cookie`,
  `Content-Language: ru`). IP те же, что у `www.gdeslon.ru` (5.189.239.194, 31.184.219.58).
- Без слэша в конце (`/api/orders`) — **301** `Location: /api/orders/`; SDK редиректы не выполняет, адрес только со слэшем.
- `Allow: GET, POST, HEAD, OPTIONS`. `GET` без тела тоже отвечает `200 []`; query-параметры GET игнорируются
  (`?state=abc` — 200). Документирован только `POST` с JSON-телом.
- Авторизация:
  - без `Authorization` — 401 `{"detail":"Некорректные учетные данные."}` за ~0,13 с;
  - неверный ключ или неверный ID — 401 `{"detail":"Недопустимые имя пользователя или пароль."}` за ~3,5 с;
  - оба с `WWW-Authenticate: Basic realm="api"`, `Content-Type: application/json`. Учётные данные в теле не возвращаются.
- **Время ответа с верными ключами — 3,6–5,6 с на любой запрос**, в том числе пустой (видимо, стоимость проверки
  ключа: неверный ключ тоже ~3,5 с). Таймаут по умолчанию 30 с достаточен; повторять запросы дорого.
- Ответ 200: `Content-Type: application/json` (без `charset`, тело UTF-8), `Content-Length`, **нет ETag,
  Last-Modified, Cache-Control** — условные запросы и кэш по валидаторам невозможны.
- Обрыва ~16 КБ, как у `api.gdeslon.ru`, у хоста нет: с `gdeslon.ru` одним соединением загружаются 72 КБ (FAQ)
  и 420 КБ (`/api/my_merchants/`). Загрузка частями (RangeTransport) не нужна и к POST не применяется.

## Форма ответа (проверено 2026-10-07 — только пустой ответ)

- Ответ — JSON-массив заказов **без обёртки**: у аккаунта автора заказов нет, на все запросы — `[]`
  (`created_at`, `transition_at`, `last_updated_at`, `confirmed_at`, `accrued_at` с `period` до 740 000 дней, а также `{}`).
- **Пагинации нет** (косвенно): постраничные ресурсы того же бэкенда (`/api/money_transaction/`,
  `/api/score_operations/`) отдают обёртку `{"total","total_pages","per_page","current_page","results"}` даже пустыми,
  а `orders` — голый `[]`. Параметров страниц документация не описывает. Значит, весь период приходит одним ответом.
- **Непустой ответ живьём не видели**: поля и их типы ниже — по документации.
- Соглашения этого бэкенда (проверено на соседних ресурсах, для заказов — догадка): десятичные числа — **строкой**
  (`/api/currencies/`: `"rate": "59.7410000000"`), валюта — **строчными** (`/api/my_merchants/`: `"currency": "rub"`),
  ID — числом.

## Тело запроса — фильтры

По документации: фильтровать можно по любому полю заказа; пример —
`{"confirmed_at": {"date": "2014-04-30", "period": 30}, "merchant_id": 2573, "state": [3, 4], "type": 0, "sub_id": 123}`
— «за период 30 дней (с 1-го по 30-е апреля)», т. е. период **заканчивается** датой `date` включительно (по документации,
на данных не проверено). Изменение статуса попадает в отчёт только на следующий день (по документации).

Поведение валидации (проверено 2026-10-07 на `gdeslon.ru`; результат у всех 200-ответов — `[]`, поэтому «200» значит
«принято», а не «фильтр работает»):

| Тело | Ответ |
|------|-------|
| пустое тело, `{}` | 200 `[]` |
| не JSON-объект: `null`, `[]`, `"x"` | **500** (HTML) |
| синтаксическая ошибка JSON | 400 `{"detail":"JSON parse error - Expecting value: line 1 column 15 (char 14)"}` |
| `Content-Type: text/plain` | 415 `{"detail":"Неподдерживаемый тип данных \"text/plain\" в запросе."}` |
| `Content-Type: application/x-www-form-urlencoded` с формой | **500** |
| `application/json; charset=utf-8` | как `application/json` |
| неизвестное поле (`foo`, `merchant_id__in`) | 200 — игнорируется или принимается молча, ошибки нет |
| `sub_id2`, `sub_id5` | 200 — так же, как неизвестное поле; работает ли фильтр, не определить |
| несколько полей даты сразу (`created_at` + `confirmed_at`) | 200 |
| дата `{"date": "2026-10-07"}` без `period`; `{"period": 30}` без `date` | 200 (значения по умолчанию неизвестны) |
| `date`: `2026-10-07 12:00:00`, `2026-10-07T12:00:00` | 200 |
| `date`: `2026-13-45`, `07.10.2026`, `null`; поле даты строкой (`"created_at": "2026-10-07"`) | **500** |
| `period`: `0`, `-5`, `30.5`, `740000`, `1000000` | 200 |
| `period`: `"30"` (строкой!), `"abc"`, `null`, `999999999` | **500** |
| `state`: `[3, 4]`, `["3", "4"]`, `[]`, `null`, `9` | 200 |
| `state`: `"abc"` | **500** |
| `type`: `1`, `[0, 1]`, `"lead"` | 200 |
| `merchant_id`: `2573`, `"2573"`, `null` | 200 |
| `merchant_id`: **`[2573]`, `[2573, 100]`** (массив), `"abc"` | **500** — фильтр по нескольким магазинам массивом не работает |
| `sub_id`: `123`, `"abc_1"`, `["a", "b"]`, кириллица (UTF-8 и `\u`-экранирование) | 200 |
| `gdeslon_order_id`: `[1, 2]` | 200 |

Ошибка 500 — статическая страница nginx `text/html`, 2 583 байта («Ошибка 500 Внутренняя ошибка сервера»), без
подробностей. Отличить неверный фильтр от сбоя сервера по ответу нельзя — фильтры нужно проверять до запроса.

## Поля заказа (по документации)

| Поле | Смысл |
|------|-------|
| `gdeslon_order_id` | ID заказа в Где Слон |
| `merchant_order_id` | номер заказа у магазина |
| `sub_id` | sub_id перехода (в FAQ ошибочно «Идентификатор заказа») |
| `merchant_id`, `merchant_name` | магазин (ID «в системе Gdeslon» — тот же, что в поиске и магазинах) |
| `affiliate_id` | ID вебмастера (партнёра) |
| `state` | 0 новый (в кабинете — «потенциальный», в postback — `created`), 1 отменён (`cancelled`), 2 отложен (`pending`), 3 подтверждён (`confirmed`), 4 выплачен (`payed`) — FAQ 26, 60, 80 |
| `type` | 0 товарный заказ, 1 лид |
| `partner_payment` | вознаграждение вебмастера |
| `order_payment` | сумма заказа |
| `currency` | валюта заказа и платежа (одна на обе суммы) |
| `items_in_order` | количество товаров |
| `transition_at` | дата и время перехода |
| `created_at` | создание |
| `last_updated_at` | последнее обновление |
| `confirmed_at` | подтверждение |
| `accrued_at` | выплата вебмастеру |
| `keywords` | ключевые слова |

`sub_id2`…`sub_id5` документация заказов не упоминает (они есть только в postback).
Для синхронизации статусов документация предлагает `last_updated_at` за период.

## Два бэкенда: `www.gdeslon.ru` (проверено 2026-10-07)

`POST https://www.gdeslon.ru/api/orders/` (адрес из документации) теперь отвечает — это **другая реализация** (Rails:
`X-Runtime`, `X-Request-Id`, `ETag: W/"<md5 тела>"`, `Content-Type: application/json; charset=utf-8`, CORS `*`):

- ~0,2 с на запрос (против 3,6–5,6 с у `gdeslon.ru`);
- авторизация настоящая: без ключей и с неверными — 401 `text/html` `HTTP Basic: Access denied.`;
- синтаксическая ошибка JSON — 400 с пустым `text/html`;
- **любые фильтры, включая неверные** (`merchant_id` массивом, дата `2026-13-45`, `period: "30"`, тело `[]`,
  `text/plain`), — 200 `[]`: валидации нет.

Ведут ли оба бэкенда к одним данным — неизвестно (заказов у аккаунта нет). SDK использует `gdeslon.ru` как канонический
хост (README), адрес настраивается.

## Открытые вопросы (проверить на аккаунте с заказами)

- поля и типы непустого ответа: ID числом или строкой, суммы строкой или числом, формат дат и часовой пояс,
  регистр и вид `currency` (`"rub"`, `"RUB"`, `"RUR"`, ID валюты?), `null` у лида в `order_payment`/`items_in_order`;
- границы периода (`date` включительно? `period: 30` — 30 или 31 день? часовой пояс «дня»);
- значения по умолчанию при `{}` и при дате без `period`; работают ли `sub_id2..5`, `type` строкой;
- есть ли в ответе `sub_id2..5`; одинаковы ли данные на `gdeslon.ru` и `www.gdeslon.ru`;
- предел размера ответа за большой период (пагинации нет).
