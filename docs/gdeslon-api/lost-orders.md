# Потерянные заказы (заявки)

Источник: https://gdeslon.ru/faq/74/, https://gdeslon.ru/faq/25/ (перечитаны 2026-10-07) · Контекст: Claims · Порт: `LostOrderClaims`

Заявка вебмастера на заказ, который не попал в статистику; рекламодатель пересматривает атрибуцию.
Авторизация: `Authorization: Bearer <токен из раздела XML API>` (https://gdeslon.ru/api_settings/xml). Ответы JSON.
FAQ 25 (интерфейс кабинета): номер, дата, сумма заказа, рекламодатель, описание; «приложите скан чека, если это
требуется» — в API (FAQ 74) `attachment` обязателен.

> `POST` создаёт реальную заявку у рекламодателя. Живьём не вызывать никогда (даже с заведомо битыми данными):
> в разработке и тестах — только фейковый транспорт. Живые пробы — только `GET`.

## HTTP и авторизация (проверено 2026-10-07)

- Бэкенд — Django REST Framework на `gdeslon.ru` (те же признаки, что у API по продажам: `Vary: Accept-Language, Cookie`,
  `Content-Language: ru`). Корень `GET /api/v1/` → `{"lost-orders": ..., "coupons": ..., "kinds": ...}` (ссылки `http://`).
- Адреса — **только со слэшем в конце**: `/api/v1/lost-orders` и `/api/v1/lost-orders/{id}` → **301** на вариант со
  слэшем (`text/html`, пустое тело). SDK редиректы не выполняет. В примерах FAQ `curl -L` — не повторять.
- `Allow` списка: `GET, POST, HEAD, OPTIONS`; одной заявки: `GET, HEAD, OPTIONS` — **изменения и удаления заявки в API нет**.
- Ответы: `Content-Type: application/json` (без `charset`, тело UTF-8, кириллица не экранирована), без `ETag`,
  `Last-Modified`, `Cache-Control`. Время ответа 0,13–0,18 с (единично 0,65 с) — в отличие от `/api/orders/` (3,6–5,6 с).
- Только JSON-рендерер: `Accept: text/html` → **406** `{"errors":{"detail":"Невозможно удовлетворить \"Accept\" заголовок запроса."}}`;
  `?format=api` → 404; `Accept: */*`, `application/json`, `application/json; charset=utf-8`, `?format=json` — 200.
- **Все ошибки — в обёртке `{"errors": {...}}`** (свой обработчик исключений, не стандартный DRF `{"detail": ...}`):

| Ситуация | Ответ |
|----------|-------|
| нет `Authorization` | 401 `{"errors":{"detail":"Недопустимый заголовок токена. Не предоставлены учетные данные."}}` |
| неверный токен | 401 `{"errors":{"detail":"Недопустимый токен."}}` (токен в ответе не повторяется) |
| схема `Token <токен>` вместо `Bearer` | 401 `{"errors":{"detail":"Учетные данные не были предоставлены."}}` |
| неверный фильтр | 400 `{"errors":{"<поле>":["<сообщение>"]}}` (значение запроса повторяется в сообщении) |
| заявки нет | 404 `{"errors":{"detail":"Не найдено."}}` |

  У 401 — `WWW-Authenticate: Bearer`.

## Список: `GET https://gdeslon.ru/api/v1/lost-orders/` (проверено 2026-10-07 — только пустой список)

- Без `limit` — **JSON-массив без обёртки** со всеми заявками: у аккаунта автора заявок нет, ответ `[]`.
- С `limit` (целое > 0) включается `LimitOffsetPagination`: `{"count":0,"next":null,"previous":null,"results":[]}`;
  `next`/`previous` — абсолютные ссылки **`http://`**gdeslon.ru/... (не переходить по ним с `Authorization`).
  `limit=0`, `-1`, `abc` — пагинации нет (массив); `offset` без `limit` игнорируется; `offset=abc` при `limit` — как 0.
  `limit=100000` принят (есть ли `max_limit` — не определить на пустых данных). Параметров `page`, `page_size` нет (игнорируются).
- Неизвестные параметры игнорируются (`foo=bar` → 200).

Фильтры (FAQ 74 + поведение живьём):

| Параметр | По документации | Живьём (проверено 2026-10-07) |
|----------|-----------------|-------------------------------|
| `ticket_id` | integer | выбор из **своих** заявок: любой чужой/несуществующий ID → 400 `Выберите корректный вариант. 1 нет среди допустимых значений.`; `abc`, пусто → 400 `“abc” является неверным значением.` Не «пустой список», а ошибка |
| `merchant_id` | integer, «список рекламодателей» | выбор из справочника магазинов: существующий (в т. ч. не подключённый к вебмастеру) — 200; `0`, `99999999999`, ID удалённого магазина из примера FAQ (54376) → 400 `… нет среди допустимых значений.`; `abc`, `1,2`, `" 1"` → 400. Повтор `merchant_id=1&merchant_id=2` — 200 (берётся одно значение) |
| `start_date`, `end_date` | `%d.%m.%Y` или `%Y-%m-%d` | оба формата — 200; `2026-13-45`, `31.02.2026`, `abc`, `2026-01-01T00:00:00`, `01/01/2026` → 400 `{"errors":{"start_date":["Введите правильную дату."]}}`. `start_date` > `end_date` — 200 (не проверяется). По какой дате фильтр (дата заказа или создания заявки) и включительны ли границы — не определить на пустых данных |
| `ticket_status` | `in_work`, `closed` | **любое значение — 200** (`foo`, `IN_WORK`, пусто): либо игнорируется, либо фильтр без проверки значения |
| `ticket_state` | не описан | **настоящий фильтр с проверкой**: `in_work`, `closed`, пусто — 200; `foo`, `new`, `open` → 400 `{"errors":{"ticket_state":["Выберите корректный вариант. foo нет среди допустимых значений."]}}`. Имя совпадает с полем ответа |
| `order_status` | `waiting`, `confirmed`, `declined` | **любое значение — 200** (`waiting`, `in_waiting`, `foo`); работает ли фильтр — не определить. Проверяемого аналога нет (`order_state`, `sale_state`, `status`, `state` — тоже 200 на `foo`) |

## Одна заявка: `GET https://gdeslon.ru/api/v1/lost-orders/{id}/`

- Несуществующий, чужой, `0`, `-1`, `abc` → 404 `{"errors":{"detail":"Не найдено."}}` (проверено 2026-10-07).
- Без токена / неверный токен — те же 401, что у списка (проверено 2026-10-07).
- Ответ 200 — объект заявки (по документации; живьём не видели — заявок нет).

## Создать заявку: `POST https://gdeslon.ru/api/v1/lost-orders/` (multipart/form-data) — по документации

| Поле | Тип | Обяз. | Ограничения |
|------|-----|-------|-------------|
| `order_id` | string | да | ≤ 255 символов |
| `order_date` | date | да | «за прошедшие 3 месяца»; `%d.%m.%Y` или `%Y-%m-%d` |
| `order_total` | float | да | «2 знака после плавающей точки» |
| `merchant_id` | integer | да | ID рекламодателя (живьём фильтр списка принимает только ID из справочника магазинов) |
| `attachment` | file | да | JPEG/JPG/PNG/PDF, «не более 10 МБ» (скан чека) |
| `description` | string | нет | ≤ 255 символов |

Не описано и живьём не проверяется (POST запрещён): HTTP-статус успеха (для DRF `CreateAPIView` обычно 201), форма
ошибок валидации (по аналогии с GET вероятно `{"errors":{"<поле>":[...]}}`), граница «3 месяцев» (календарные месяцы или
дни, часовой пояс), 10 МБ = 10 000 000 или 10 485 760 байт, лимит тела у nginx (413), проверяется ли содержимое файла или
только расширение, реакция на повторную заявку с тем же `order_id`, допустимы ли будущие даты и `order_total` = 0.

## Поля заявки (по документации)

Пример ответа создания (FAQ 74):

```json
{"id": 5796, "order_id": "2342lost", "order_date": "2021-06-28", "description": "...",
 "attachment": "http://gdeslon.ru/uploads/ticket/path/to/file.jpg", "merchant_id": 54376,
 "merchant_name": "merchant.com", "order_updated_date": "2021-07-27", "order_total": 12020.22,
 "order_status": "in_waiting", "ticket_state": "in_work"}
```

| Поле | Смысл | Замечания |
|------|-------|-----------|
| `id` | ID заявки | в таблице полей списка не указан, но есть в примере |
| `order_id` | номер заказа (у магазина) | строка |
| `order_date` | дата заказа | `Y-m-d` |
| `description` | описание заявки | в примере списка `""` |
| `attachment` | путь до загруженного файла | абсолютный URL `http://gdeslon.ru/uploads/...` |
| `merchant_id`, `merchant_name` | рекламодатель | |
| `order_updated_date` | дата обновления данных по заказу | в примере **списка** вместо него `sale_updated_at` |
| `order_total` | сумма заказа | JSON-число (`12020.22`, `12312.00`); **валюты нет** |
| `order_status` | статус заказа | в примере создания `in_waiting`, в фильтре — `waiting`; ещё `confirmed`, `declined` |
| `ticket_state` | статус заявки | `in_work`, `closed` (в фильтре FAQ — `ticket_status`, но проверяется `ticket_state`) |

## Расхождения документации (итог на 2026-10-07)

- статус заказа: в ответе `in_waiting`, в фильтре `waiting` — не проверено (нет заявок); разбор принимает оба;
- поле даты обновления: `order_updated_date` (создание) vs `sale_updated_at` (список) — не проверено; разбор принимает оба;
- фильтр статуса заявки: документирован `ticket_status` (значение не проверяется), а проверяемый фильтр — `ticket_state`
  (проверено 2026-10-07);
- пример ответа списка в FAQ — одиночный объект; на деле список — JSON-массив (проверено 2026-10-07);
- `curl -L` в примерах: без слэша — 301 (проверено 2026-10-07);
- FAQ 25: скан чека «если требуется», FAQ 74: `attachment` обязателен.

## Открытые вопросы (проверить на аккаунте с заявками, только GET)

- форма и типы непустого списка и одной заявки (ID числом? `order_total` числом или строкой? `attachment` — `null`?);
- значения `order_status` (`in_waiting` или `waiting`) и имя поля даты обновления;
- работают ли `ticket_status` и `order_status`; по какой дате фильтруют `start_date`/`end_date`;
- есть ли серверный размер страницы (`max_limit`) и появится ли обёртка без `limit`.
